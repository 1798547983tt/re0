# 《Re:Zero》状态变量系统 PRD

## Problem Statement

现有状态层无法完整表达《Re:Zero》的时间层、轮回分支和角色关系；若只记录普通数值，世界时间无法表达轮回分支，菜月昴死亡时也无法在非菜月昴主角档案下触发世界重启，关系和事件会随着聊天增长而失控。

本项目已经有正传第 01–39 卷、剧情时间线和人物档案。变量层的职责应当是记录当前可变状态，而不是重复世界书中的原作资料、证据、置信度或角色知识边界。与此同时，MVU 加载脚本和 `stat_data` 注入模板是既有兼容边界，不能修改。

## Solution

建立一套以《Re:Zero》世界状态为中心的 MVU 变量协议：保留既有 MVU 加载脚本与状态注入模板，只重写可编辑的初始状态、更新规则、输出格式和 ZOD schema。

系统以初始化时锁定的“主角档案”为唯一主角。主角可以是任意原作人物或原创角色，聊天期间不可切换；菜月昴无论是否是主角，都必须在系统中恰好保留一份动态状态。当前运行世界中，菜月昴每次被叙事明确确认实际死亡时，系统登记一条死亡事件并增加一次世界重启次数；世界随后回到死亡回归存档点，主线世界时间沿用存档点，失败路线的可变状态不污染重启后的世界。

变量只记录状态，不承载世界书职责。原作资料、资料来源、资料置信度、角色知识上限、人物性格和静态背景由世界书提供，不进入变量树。

## User Stories

1. 作为开局用户，我希望用自然语言创建任意原作人物或原创角色的主角档案，以便不受固定菜月昴主角限制。
2. 作为开局用户，我希望主角在第一轮初始化后被锁定，以便叙事过程中不会因为模型误判而切换控制对象。
3. 作为开局用户，我希望只提供已知信息，未提供的状态保持“未知/未确认”，以便系统不擅自编造人物设定。
4. 作为开局用户，我希望指定主线、轮回分支、历史回溯或试炼幻境的起点，以便世界时间层与仓库既有时间线一致。
5. 作为玩家，我希望看到规范日期、粗粒度时段、时间层和当前轮回分支，以便区分世界实际时间与轮回记忆。
6. 作为玩家，我希望看到国家、地区、场所和具体位置，以便行动结果受地点与场地影响。
7. 作为玩家，我希望看到天气、光照和环境描述，以便环境变化成为可追踪状态而不是散落在叙事中。
8. 作为玩家，我希望看到危机等级、世界动向和势力态势，以便长期事件不会在多轮对话中消失。
9. 作为主角扮演者，我希望看到生命、体力、魔力、精神稳定、伤势和异常状态，以便判断当前是否能继续行动。
10. 作为主角扮演者，我希望看到门状态、门负荷、魔女余香、当前形态和可战状态，以便表达《Re:Zero》的能力限制。
11. 作为主角扮演者，我希望看到加护、权能、魔法、精灵术、种族能力、武技和一般技能的当前状态，以便能力使用受条件约束。
12. 作为主角扮演者，我希望看到当前目标，以便每次行动都能与正在进行的事件关联。
13. 作为非菜月昴主角，我希望菜月昴仍被持续追踪，以便他的死亡可以触发世界重启。
14. 作为玩家，我希望濒死、昏迷、失踪、生死未卜、幻觉、替身死亡和试炼影像不会误触发世界重启。
15. 作为玩家，我希望菜月昴每次实际死亡只增加一次重启次数，即使同一事件被分段描写，也不会重复计数。
16. 作为玩家，我希望每次重启都记录菜月昴如何死亡，以便回顾失败路线的关键因果。
17. 作为菜月昴的扮演者，我希望死亡记录保留少量本轮遗留情报，以便下一轮能基于亲历信息改变行动。
18. 作为玩家，我希望死亡记录和重启次数不随存档点回滚，以便世界轮回具有可追溯账本。
19. 作为玩家，我希望重启后的世界状态完整回到存档点，以便 NPC、事件、线索、资产和地点不会混入失败路线。
20. 作为玩家，我希望存档点只能由明确的剧情机制推进，以便模型不会因普通换场或闲聊随意改写不可逆进度。
21. 作为玩家，我希望保留已确认的伴侣关系，但不把普通同伴误写成恋爱关系。
22. 作为玩家，我希望契约伙伴单独记录，并与一般人物关系区分，以便精灵、契约对象和长期绑定伙伴保持原作语义。
23. 作为玩家，我希望其他盟友、敌人、亲属和政治人物只在当前剧情相关时进入人物表，以便变量不会加载全部 153 份人物档案。
24. 作为玩家，我希望关系数值能够表达敌意与信任差异，以便好感、信任、关系阶段和立场不会互相替代。
25. 作为玩家，我希望人物的当前位置、当前行动、生存状态、生命、魔力、伤势和异常状态能随事件更新，以便关系表反映当前世界而不是静态人设。
26. 作为玩家，我希望追踪进行中的事件和近期事件记录，以便多个剧情线能同时推进。
27. 作为调查者，我希望追踪当前线索和未解问题，以便调查进度在重启前后按规则回滚或保留。
28. 作为玩家，我希望物品、装备、货币和据点记录持有者、存放位置、数量、损耗和效果，以便资源变化可验证。
29. 作为玩家，我希望每次回复都有变量更新块，即使没有状态变化也要明确写出“无变化”，以便检查模型是否遗漏状态。
30. 作为玩家，我希望变量更新只在正文有因果依据时改变生命、关系或能力数值，以便系统不通过无意义的数值抖动伪装成活跃。
31. 作为维护者，我希望 ZOD 负责类型、默认值、枚举、范围和有限历史裁剪，而不暗中执行世界重启，以便状态写入职责清晰。
32. 作为维护者，我希望新增人物、事件、线索和资产使用稳定键，以便改名、迁移和删除不会破坏路径。
33. 作为维护者，我希望初始化、普通推进、死亡重启、关系迁移和清理都有可测试的外部行为，以便真实 SillyTavern 验收不依赖猜测。

## Implementation Decisions

### 1. 兼容边界与可编辑范围

- 既有 MVU 加载脚本保持字节级不变。
- 既有 `stat_data` 状态注入模板保持不变。
- 初始化树、变量更新规则、变量输出格式和 ZOD schema 是本系统的可编辑协议层。
- 变量使用纯值结构，不使用旧式 `[value, description]` 二元组。
- 模型输出的 JSON Patch 只使用 `add`、`replace`、`remove`、`move`。新增 record 项先 `add` 完整对象；已有路径才使用 `replace`。`delta` 与 `insert` 不作为模型输出要求。

### 2. 顶层状态树

状态树的顶层对象固定为：

```text
世界 / 主角档案 / 轮回 / 关系 / 事件 / 线索 / 资产 / 规则
```

`规则`只保存运行时锁定与 schema 版本等状态元数据，不保存世界书规则、资料来源、置信度或角色知识。

### 3. 世界

```text
世界:
  当前时间:
    规范日期
    时段
    时间层              # 主线 / 轮回分支 / 历史回溯 / 试炼幻境
    轮回分支
  当前地点:
    国家
    地区
    场所
    具体位置
  环境:
    天气
    光照
    描述
  危机等级             # 无 / 低 / 中 / 高 / 灾难
  动向:                 # 保持 2–3 条
    事件ID:
      标题 / 阶段 / 类型 / 地点 / 描述
  势力态势:
    势力名:
      立场 / 状态 / 描述
```

规范日期遵循仓库既有魔女历演算；原文无绝对日期时继续使用编辑演算标记。死亡回归只重置世界时间到存档点，不把菜月昴的主观记忆时间累加到世界时间。

### 4. 主角档案

主角档案在初始化时创建并锁定，聊天期间不可切换。它包含基础身份、当前可变状态和能力状态，不复制世界书中的静态性格、背景或证据字段：

```text
主角档案:
  主角锁定
  姓名 / 角色类型 / 性别 / 年龄阶段 / 种族
  身份 / 阵营 / 容貌 / 衣着
  生存状态             # 存活 / 濒死 / 昏迷 / 失踪 / 死亡
  生命 / 体力 / 魔力 / 精神稳定   # 0–100 叙事仪表
  门状态 / 门负荷 / 魔女余香
  伤势:
    伤势ID: 部位 / 程度 / 描述
  异常状态:
    状态ID: 类型 / 剩余表现 / 描述
  当前形态
  战力等阶:
    阶数 / 位阶 / 可战状态 / 生效条件
  能力:
    加护 / 权能 / 魔法 / 精灵术 / 种族能力 / 武技 / 一般技能
  当前目标
```

所有 0–100 字段是叙事仪表，不是原作官方属性，不单独决定战斗胜负。`生命=0`不自动等于死亡；只有叙事明确确认死亡时才将 `生存状态`写为死亡并触发重启判定。

### 5. 轮回与跨轮回账本

```text
轮回:
  世界重启次数: 0
  当前轮回编号: 0
  存档点:
    有效
    创建时间
    状态快照: 世界 / 主角档案 / 关系 / 事件 / 线索 / 资产
  最近一次重启:
    死亡事件ID / 重启编号 / 触发时间 / 恢复结果
  菜月昴死亡记录:
    死亡ID:
      重启编号
      死亡时规范日期与时段
      死亡时地点
      直接原因
      死亡经过与最后行动
      在场或相关人物
      触发前轮回分支
      本轮遗留情报: 最多 5 条
  最近一次死亡: 死亡记录镜像
```

死亡记录与世界重启次数是跨轮回账本，不被存档快照覆盖；其他世界状态均属于快照范围。历史回溯、试炼幻境和未落地的 IF 假设不计入世界重启次数。一次实际死亡必须有唯一死亡 ID；同一 ID 已处理时不得再次递增计数。

世界重启的逻辑顺序为：

1. 确认死亡对象是当前世界中的菜月昴，且死亡是明确的实际死亡。
2. 追加一条菜月昴死亡记录。
3. 将世界重启次数和当前轮回编号各增加一次。
4. 写入最近一次重启与最近一次死亡镜像。
5. 先把存档点快照中的世界、主角档案、关系、事件、线索和资产写回各顶层容器；存档点自身不在恢复集合中，不得被嵌套快照递归覆盖。
6. 为下一轮保留菜月昴带回的遗留情报；其他角色默认不保留失败轮回记忆。

上述步骤必须在同一个 `UpdateVariable` 块内完成。恢复只替换六个可变顶层容器，不替换 `轮回` 根对象；这样既避免递归快照，也不会覆盖刚追加的死亡记录和计数。该批量 Patch 是否具备目标运行时所需的一致性，仍须通过真实运行测试确认。

### 6. 关系

```text
关系:
  伴侣:
    规范姓名:
      关系阶段 / 亲密度 / 立场 / 生存状态 / 当前地点 / 当前行动
  契约伙伴:
    规范姓名:
      契约状态 / 关系阶段 / 信任 / 立场 / 生存状态 / 当前地点 / 当前行动
  人物:
    规范姓名:
      身份 / 阵营 / 关系阶段 / 立场
      好感(-100..100) / 信任(0..100)
      生存状态 / 生命 / 魔力 / 伤势 / 异常状态
      当前地点 / 当前行动 / 当前形态
```

人物表只追踪近期登场、同行、失踪或会影响当前事件的人物；不把全部人物档案复制进变量。菜月昴必须始终存在一份：若他不是主角，则固定存在于 `关系.人物.菜月昴`；若他是主角，则只存在于 `主角档案`。

同一人物不得同时出现在两个关系容器。关系迁移必须先把完整对象写入目标容器，再删除旧容器；迁移后同步相关事件和消息状态。

### 7. 事件、线索与资产

```text
事件:
  进行中:
    事件ID:
      标题 / 类型 / 阶段 / 状态 / 地点 / 参与者 / 目标 / 描述
  近期记录:               # 最多 12 条
    事件ID:
      标题 / 结果 / 规范日期 / 参与者 / 描述

线索:
  当前线索:                # 最多 30 条
    线索ID:
      标题 / 状态 / 关联事件 / 描述 / 下一步
  未解问题: []

资产:
  货币:
    货币类型: 数量 / 持有者 / 存放位置
  物品:
    物品ID:
      名称 / 数量 / 持有者 / 存放位置 / 描述
  装备:
    装备ID:
      名称 / 持有者 / 装备状态 / 损耗 / 当前效果
  据点与存放:
    据点ID:
      名称 / 位置 / 控制者 / 状态
```

事件和线索随世界重启回滚；只有死亡记录内的精简遗留情报跨轮回保留。近期事件最多 12 条、当前线索最多 30 条；裁剪从最旧且已结束的记录开始，不删除进行中事件、未解问题或死亡账本。

### 8. 初始化契约

第一次收到开局信息时，模型必须抽取并初始化：主角锁定信息、世界时间与地点、时间层、主角基础身份、阵营、能力、当前状态、初始关系、资产、进行中事件、当前线索、存档点和空的跨轮回账本。

没有提供的字段使用 schema 默认值 `未知`、`无`、空对象或空数组；不得把世界书中的人物资料自动写成当前状态。初始化时若读取到不属于本协议的遗留顶层键，直接清理而不迁移。初始化完成后立即创建第一份有效存档点。主角锁定字段一旦建立，不允许后续更新为另一名角色。

### 9. 每回合更新契约

每次回复都输出一个更新块，并在分析中依次检查：

1. 初始化是否刚完成；
2. 世界时间、地点和环境是否变化；
3. 危机等级、世界动向和势力态势；
4. 主角生存、资源、伤势、异常、门与能力状态；
5. 关系容器及人物状态；
6. 进行中事件、近期记录、当前线索和未解问题；
7. 资产的获得、消耗、转移和损耗；
8. 存档点是否因明确剧情机制推进；
9. 是否出现“明确的菜月昴实际死亡”，以及死亡 ID 是否已经处理；
10. 若无变化，明确写 `no change`，不制造无因果数值变化。

### 10. ZOD 职责与数据安全

- ZOD 只负责结构验证、默认值、枚举、0–100 数值钳制和有限列表裁剪。
- 所有动态 record 项允许稳定键；对象项使用宽松但有明确字段的 schema，避免未知动态人物被静默剥离。
- ZOD 不监听事件、不判断死亡、不创建存档点、不执行回档。
- 世界重启、关系迁移、事件推进和存档点更新全部由世界书规则指导模型生成 JSON Patch。
- 变量更新规则不得要求模型写入资料来源、置信度、知识边界、静态性格或原作背景字段。

### 11. 运行依赖与交付边界

目标是 SillyTavern 的 V2/V3 兼容角色卡变量协议，依赖宿主已启用的 Tavern Helper/MVU 能力以及固定的远程 MVU bundle。固定 loader 与状态注入模板不在本需求中迁移或升级；远程 bundle 版本、网络可用性和 ZOD 注册行为必须在真实 SillyTavern 中单独验收。

## Testing Decisions

测试只验证外部状态行为和持久化结果，不测试 ZOD 内部实现细节或世界书提示词措辞。最高测试缝是“同一套变量协议在 MVU 中读入当前状态并应用 UpdateVariable 后得到的 `stat_data`”。

必须覆盖以下场景：

1. 空状态初始化：自然语言开局能生成完整主角档案、世界状态和第一存档点。
2. 主角锁定：初始化后尝试切换角色会被拒绝或保持原主角。
3. 任意主角：原作人物和原创角色都能初始化，不依赖菜月昴专属字段。
4. 普通推进：时间、地点、危机、关系、事件、线索和资产能按因果更新。
5. 无变化回合：纯对话不会强制抖动数值，分析仍覆盖检查清单。
6. 非昴主角追踪：菜月昴自动存在于人物表且不会因离场被清理。
7. 非死亡状态：濒死、昏迷、失踪、幻觉、试炼影像和替身死亡不增加重启次数。
8. 菜月昴死亡：追加一条完整死亡记录，重启次数和轮回编号各增加一次，状态回到存档点。
9. 同一死亡去重：重复处理同一死亡 ID 不再增加计数或追加重复记录。
10. 死亡记录持久化：多次重启后旧记录仍存在，最近一次镜像与账本一致。
11. 快照隔离：失败轮回中的 NPC、事件、线索、资产和地点不会泄漏到重启后状态。
12. 记忆边界：只有菜月昴死亡记录中的精简遗留情报跨轮回保留，其他角色状态回到快照。
13. 存档点门控：普通换场或闲聊不能修改存档点；明确推进事件可以更新存档点。
14. 关系迁移：人物从人物表迁入伴侣或契约伙伴时不存在双存，完整字段不丢失。
15. 关系数值：好感可表达 -100 到 100，信任保持 0 到 100，超界值被钳制。
16. 历史裁剪：近期事件最多 12 条、线索最多 30 条，进行中和未解项目不被错误删除。
17. Patch 方言：模型输出缺少前导斜杠、对不存在路径使用 replace、或使用未允许 op 时能被测试识别。
18. 固定件回归：固定 MVU loader 和 `stat_data` 注入模板的内容未被修改。
19. ZOD 注册：宿主全局 Zod 与注册 helper 在目标运行时可用，schema 不会静默剥离合法动态记录。
20. 真实运行验收：在目标 SillyTavern 中完成初始化、普通推进、菜月昴死亡、原子重启和回读五条 smoke 流程。

仓库现有的人物档案校验测试继续作为资料层回归；变量系统新增独立的 schema/协议静态检查和 MVU 场景测试，不把人物档案证据测试与状态变量测试混为一套。

## Out of Scope

- 不修改既有 MVU 加载脚本或 `stat_data` 注入模板。
- 不把世界书中的原作资料、来源、置信度、知识边界、静态性格和人物背景复制进变量。
- 不实现状态栏 UI、前端控制中心、图片/PNG 打包、角色卡发布或远程部署。
- 不自动生成完整 153 人动态状态；只追踪当前剧情相关人物和菜月昴。
- 不把生命、魔力、精神稳定或战力等阶当作原作官方数值或胜负公式。
- 不为历史回溯、试炼幻境或未落地 IF 假设增加世界重启次数。
- 不允许聊天中途切换主角档案。
- 不在 ZOD 或辅助脚本中暗中执行死亡判定、存档推进或世界回档。
- 不实现与当前状态协议无关的附加演出模块；关系使用伴侣、契约伙伴和人物三类 Re:Zero 语义容器。

## Further Notes

- 项目规范日期、世界时间、轮回分支和时间层必须继续遵守现有时间线 ADR；日期没有原作绝对依据时标记为编辑演算或历史估算。
- `主角档案`是锁定的领域术语，避免再使用“视角角色”造成可切换的误解。
- `世界重启次数`与`菜月昴死亡记录`是跨轮回账本；存档点只覆盖可变世界状态。
- 固定 MVU bundle 的实现支持 `replace`、`delta`、`insert/add`、`remove` 和 `move`，但模型输出协议主动收窄为 `add/replace/remove/move`，以保持可审计性。
- 根状态替换是否能在目标版本中可靠完成重启，需要真实 SillyTavern 验收；若不通过，必须在不改变固定件的前提下重新设计恢复 Patch，而不是声称已经具备事务性。
- 本 PRD 描述的是可实施的状态协议，不是最终角色卡成品。完成实现后必须提供字段 ledger、初始化样例、重启样例、静态检查结果和真实运行证据。
